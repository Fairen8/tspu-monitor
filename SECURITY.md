# Политика безопасности

## Поддерживаемые версии

| Версия | Поддержка |
|---|---|
| 2.0.x | да |
| 1.x | нет |

## Как сообщить об уязвимости

Используйте **приватный канал** — не создавайте публичный issue:

1. GitHub → вкладка **Security** → **Report a vulnerability**
   (Private Vulnerability Reporting).
2. Если функция недоступна — свяжитесь с владельцем репозитория
   (@Fairen8) через GitHub.

В сообщении укажите:

* версию (`tspu-monitor version`) и способ развёртывания (Docker/LXC/VM);
* тип проблемы (RCE, утечка секретов, обход авторизации, инъекция, DoS);
* шаги воспроизведения и минимальный пример;
* возможное влияние и предложение по исправлению (если есть).

Не прикладывайте реальные токены, IP-адреса и конфиги — замените их
плейсхолдерами.

## Что мы считаем уязвимостью

* выполнение произвольного кода через конфигурацию, webhook-ответ,
  Telegram-апдейт или результат пробы;
* утечка секретов из `secrets.yaml`, webhook-токена, Telegram-токена;
* обход whitelist Telegram-пользователей;
* SSRF/инъекции при обработке URL, заголовков, JSON;
* отказ в обслуживании, приводящий к падению демона.

## Что уязвимостью не является

* результаты диагностики (блокировки, заглушки, DPI) — это предметная
  область, а не дефект;
* недоступность внешних сервисов из-за фильтрации провайдера;
* проброс портов в конфигурации пользователя.

## Процесс

1. Подтверждение получения — до 72 часов.
2. Первичная оценка и план исправления — до 7 дней.
3. Исправление выходит патч-релизом; после публикации — запись в
   `CHANGELOG.md` (раздел Security).
4. Автор отчёта указывается в благодарностях (по желанию).

## Рекомендации по безопасной эксплуатации

* `secrets.yaml` — только `chmod 600`, вне git.
* Telegram-бот — обязательно `allowed_users`; токен ротируйте при утечке.
* Webhook — используйте отдельный токен и HTTPS.
* Docker — не публикуйте порты контейнера; монтируйте конфиг только для чтения, если он не меняется.
* Обновляйте зависимости (Dependabot включён) и следите за релизами.
